    - Expose `val currentMultiplier: StateFlow<Int>` — computed as `wakeLockMultiplier * batterySaverMultiplier`. Use a MutableStateFlow that updates when either multiplier changes.
    - Add `fun onWakeLockReleased()`:

      - Update `_currentMultiplier` StateFlow
      - If tracking, restart with adaptive interval (applies new multiplier)
      - Log: "Wake lock released, location multiplier now ${currentMultiplier.value}x"
    - Add `fun onWakeLockAcquired()`:
      - Gradual ramp-up: don't immediately set multiplier to 1. Instead:
        - Set a flag `wakeLockRecoveryCycles = 2` (1-2 cycles of current interval before returning to 1x)
        - After each location update callback (in `onLocationUpdate`), decrement `wakeLockRecoveryCycles`. When it reaches 0, set `wakeLockMultiplier = 1` and restart tracking.
      - This implements "gradual ramp-up over 1-2 cycles when audio resumes" per user decision.
      - Update `_currentMultiplier` StateFlow on each change
      - Log: "Wake lock acquired, location recovery in $wakeLockRecoveryCycles cycles"
    - Add `fun onBatterySaverChanged(enabled: Boolean)`:
      - If enabled: set `batterySaverMultiplier = 4`, update StateFlow, restart tracking
      - If disabled: set `batterySaverMultiplier = 1`, update StateFlow, restart tracking IMMEDIATELY (per user decision: "Immediate location snap-back when battery saver is disabled")
      - IMPORTANT: When battery saver is disabled, snap-back is immediate regardless of wake lock state. But final interval still accounts for current wake lock multiplier. So if wake lock is released AND battery saver disables: multiplier = 2 * 1 = 2x (not 1x). This avoids pitfall #3 from research.
      - Log: "Battery saver changed to $enabled, location multiplier now ${currentMultiplier.value}x"
